# Lab probe: registry strings, the TS011F's timer, the Sengled (2026-11-14)

Probe date: 2026-11-14. Scope: the device strings each network gives Home Assistant, which the device classes
(`hue`, `tuya_zcl`, `tuya_mcu`, `sengled`, `other`) read, and how a Tuya TS011F plug and a Sengled E11-G13 bulb answer
the Zigbee `OnWithTimedOff` command (cluster `0x0006`, command `0x42`). It spans Zigbee2MQTT, ZHA, Hue and Matter and
lives in this bundle because most cases ran here. Spec: `docs/plans/2026-11-14-device-classes.md`, step 3, "Lab probe".

Versions: Home Assistant 2026.10.4, Zigbee2MQTT 2.14.3 with zigbee-herdsman-converters (ZHC) 26.125.0, Hue Bridge `BSB002`
software `6.3.1978545030`. Roles are generic (`TS011F plug`, `Hue bulb`); no names, IDs or addresses.

## Method, and where it departed from the spec

- Commands went straight from a script: Z2M by `mqtt.publish` to the device's `set` topic, ZHA by
  `zha.issue_zigbee_cluster_command`. Reads once a second: Z2M by a `genOnOff` read of `onOff`, `onTime` and
  `offWaitTime`; ZHA by the `zha/devices/clusters/attributes/value` websocket command.
- Z2M 2.14 logs a read's answer at info as `zhc:tz: Read result of 'genOnOff': {...}`, not as a `readResponse` line.
- Z2M sends no debug lines over `bridge/logging`, so the herdsman `zh:` frames (the ZCL commands C6 and C7 put on the
  air, in order) were not observed.
- C3 and C4 were skipped on the TS011F: C5 worked.
- The ZHA cases ran on a second TS011F already paired to ZHA (another firmware, below), not on the Z2M unit re-paired.

## 2. The TS011F and `OnWithTimedOff`

`0x42` fields are `(on_off_control, on_time, off_wait_time)`; ZCL units are tenths. Outcome `works` means on within
2 s of the last call and off by itself at 10 ± 2 s.

| Network, firmware | Case | Pre | Call | Status | Baseline onTime / offWaitTime | First read after | Counts down | State changes (t s) | At 125 s | Outcome |
|---|---|---|---|---|---|---|---|---|---|---|
| Z2M, `_TZ3000_0zfrhq4i` | C1 | off | `0x42 (0, 100, 0)` | Invoked | 0 / 0 | 100 / 0 | no | none | off | none |
| Z2M | C2 | off | `0x42 (0, 10, 0)` | Invoked | 0 / 0 | 10 / 0 | no | none | off | none |
| Z2M | C5 | on | `0x42 (0, 10, 10)` | Invoked | 0 / 0 | 10 / 10 | no reads between | 10.2: off | off | works |
| Z2M | C6 | off | `{"state": "ON", "on_time": 10}` | error: `No converter available for 'on_time'` | 0 / 0 | 0 / 0 | | 0.1: on | on | on, never off |
| Z2M | C7 | off | `{"state": "ON", "countdown": 10}` | ok | 0 / 0 | 10 / 10 at 1.1 s | no reads between | 0.1: on, 10.3: off | off | works |
| ZHA, `_TZ3000_typdpbpg` | C5 | on | `0x42 (0, 10, 10)` | ok | 0 / 0 | 10 / 10 at 1.1 s | by 1 a second, both fields | 12.1: off (Home Assistant's poll) | off | works |
| ZHA | C1 | off | `0x42 (0, 100, 0)` | ok | 0 / 0 | 100 / 100 at 1.1 s | by 1 a second, while off | 106.2: on | on | delayed on at 106 s |

Reads where a value changed, plus the first and last (`t | onOff | onTime | offWaitTime`):

- Z2M C1: `0.1 | 0 | 100 | 0`, `124.1 | 0 | 100 | 0`.
- Z2M C2: `0.1 | 0 | 10 | 0`, `124.1 | 0 | 10 | 0`.
- Z2M C5: `0.1 | 1 | 10 | 10`, `11.1 | 0 | 0 | 0`, `124.1 | 0 | 0 | 0`.
- Z2M C6: `0.1 | 1 | 0 | 0`, `124.1 | 1 | 0 | 0`.
- Z2M C7: `0.1 | 1 | 0 | 0`, `1.1 | 1 | 10 | 10`, `11.1 | 0 | 0 | 0`, `124.1 | 0 | 0 | 0`.
- ZHA C5: `0.1 | 1 | 0 | 10`, `1.1 | 1 | 10 | 10`, then both fields down by 1 each second to `11.1 | 1 | 0 | 0`,
  `12.1 | 0 | 0 | 0`, `124.2 | 0 | 0 | 0`.
- ZHA C1: `0.1 | 0 | 0 | 0`, `1.1 | 0 | 100 | 100`, then both fields down by 1 each second while off, to
  `105.2 | 0 | 0 | 0`, `106.2 | 1 | 0 | 0`, `124.2 | 1 | 0 | 0`.

Findings:

- **Tuya's recipe works on both firmwares:** a plain On, then `0x42` with `on_time` and `off_wait_time` both the
  duration in whole seconds (C5). Z2M's own Tuya `countdown` (C7) does the same: the reads after it match C5's.
- **DeviceSide's call (C1, tenths, from off) fails on both, differently.** `_TZ3000_0zfrhq4i` stores the value and
  never counts it down while off; the plug stays off. `_TZ3000_typdpbpg` copies `on_time` into both fields, counts
  them down in seconds while off, and switches on when they reach 0: a 10 s request in tenths turned it on 106 s
  later and left it on. The two plugs, each probed on one network only, differ, by firmware or by path (not proven); which other `_TZ3000_…` strings follow which is unknown.
- **Whole seconds from off (C2) does nothing** on `_TZ3000_0zfrhq4i`: the timer needs the plug on first.
- **Z2M drops `on_time` for `TS011F_plug_1`** (C6): the definition has no `on_time` converter, so DeviceSide's Z2M
  publish turns the plug on and sets no timer.

Decision rule 2 of the spec applies: C5 and C7 work, so the TS011F is `tuya_zcl`, not yet supported on `turn_on_for`
(the Tuya countdown pattern, deferred). The plan's Decision 16 then kept a doesn't-work entry for today's call, which the probe shows fails on both plugs.

## 3. The Sengled E11-G13 on Z2M

- `onTime` and `offWaitTime` reads answer `UNSUPPORTED_ATTRIBUTE`: the bulb has no timer attributes. Only `onOff`
  was read.

| Case | Pre | Call | Status | State changes (t s) | At 125 s | Outcome |
|---|---|---|---|---|---|---|
| C1 | off | `0x42 (0, 100, 0)` | Invoked, no error | none | off | none |
| C6 | off | `{"state": "ON", "on_time": 10}` | no log line | none | off | none |
| C2 | off | `0x42 (0, 10, 0)` | Invoked, no error | none | off | none |
| C5 | on | `0x42 (0, 10, 10)` | Invoked, no error | none | on | on, never off |

On Z2M the bulb ignores `0x42` silently, in tenths or whole seconds, from off or on; on ZHA the same command by
unicast is rejected `UNSUP_CLUSTER_COMMAND` (`docs/integrations/zha/internals.md`, Groups). Z2M's light converter
sends `0x42` alone for `on_time` (research
[2026-11-14-timed-on-call-patterns.md](2026-11-14-timed-on-call-patterns.md), §2), so DeviceSide's Z2M publish
leaves the bulb off. No Tuya-style recipe applies: the Sengled has no timer to drive.
